## 1. Критические баги

### БАГ-1. Shadowing переменных сломан (нарушение базы)

`semantics.md §5` и базовое ТЗ («перекрытие имён допускается») обещают:

```
var x: int32 = 1;
{
    var x: int32 = 2;
    print(x);           // 2
}
print(x);               // должно быть 1
```

**Фактически печатает `2 2`.** Причина: IR идентифицирует переменные только по имени
([ir.cppm:58](src/ir/ir.cppm#L58) — `Operand::var(name)`), а эмиттер заводит **одну alloca на имя
на всю функцию** ([llvm_emit.cppm:559-573](src/codegen/llvm_emit.cppm#L559-L573)). Две одноимённые
переменные из разных блоков сливаются в одну ячейку.

Хуже: если типы разные —

```
var x: int32 = 1;
{ var x: string = "hello"; }
```

— эмиттер берёт тип **первой** переменной ([llvm_emit.cppm:456-458](src/codegen/llvm_emit.cppm#L456-L458),
`if (cur.empty())`), генерируется невалидный LLVM IR, и компиляция падает с сырой ошибкой clang:
`'%t4' defined with type '%struct.herta_string' but expected 'i32'`.

**Как чинить:** при lowering переименовывать переменные уникально (например `x.1`, `x.2` по счётчику
области видимости) — семантика уже знает scope, достаточно прокинуть уникальное имя в `Operand::var`.

### БАГ-2. `a.b.c = v` молча теряет запись — вопреки собственной спецификации

`semantics.md §2.1` в таблице явно заявляет: `a.b.c = v` — «поле во вложенной структуре (база —
переменная)» — **работает**. Проверка:

```
struct Inner { c: int32, }
struct Outer { b: Inner, }
var a: Outer = Outer { b: Inner { c: 1 } };
a.b.c = 42;
print(a.b.c);   // печатает 1, запись потеряна
```

Причина: [ir.cppm:540-547](src/ir/ir.cppm#L540-L547) — для цели `FieldExpr` база лоуэрится через
`lower_expr`, что для вложенного поля даёт `LoadField` во **временную копию**; `StoreField` пишет
в копию. Документация честно описывает это ограничение для `m.points[i].x`, но `a.b.c` она относит
к рабочим случаям — и это неправда. Опаснее всего то, что ошибки нет: код компилируется и молча
делает не то.

**Как чинить (минимум):** в семантике запрещать присваивание с вложенной базой-полем (как сделано
для указателей на функции), пока lowering не научится строить цепочку GEP по lvalue.

### БАГ-3. `&s.x` и `&a[i]` дают указатель на копию — запись молча теряется

```
var s: S = S { x: 1 };
let p: *int32 = &s.x;
*p = 42;
print(s.x);   // 1 — запись ушла в копию

var a: [int32; 3] = [1, 2, 3];
let q: *int32 = &a[1];
*q = 99;
print(a[1]);  // 2 — то же самое
```

Семантика разрешает `&` на Field/Index ([semantic.cppm:1004](src/semantic/semantic.cppm#L1004)),
но lowering (`ir.cppm:643-653`) берёт адрес **временного temp**, куда значение уже скопировано.
Особая ирония: `semantics.md §2.1` рекомендует указатели как *обходной путь* для БАГ-2 — этот
обходной путь работает только для `&переменная`, а для `&поле`/`&элемент` сам страдает той же
болезнью. Комментарий в [ir.cppm:645-647](src/ir/ir.cppm#L645-L647) («Field и Index лоуэрятся через
временную alloca на стороне LLVM») показывает, что это известно, — но тогда это должно быть ошибкой
компиляции, а не тихой потерей записи.

### БАГ-4. `print(указатель)` — невалидный LLVM IR, наружу утекает ошибка clang

```
var p: *int32 = &x;
print(p);
```

→ `error: clang failed (1): ... '%t4' defined with type 'ptr' but expected 'i64'`.

`check_builtin_print` ([semantic.cppm:1443](src/semantic/semantic.cppm#L1443)) отклоняет только
void/array/struct и пропускает указатели, а эмиттер шлёт `ptr` в `@herta_print_int(i64)`.
`semantics.md §10` говорит «любой встроенный скалярный тип или string» — указатель под это
определение не подпадает; семантика должна его отклонять.

## 2. Существенные недочёты

### Н-1. Кросс-модульный доступ работает **только для функций** — спецификация обещает больше

`semantics.md §13.3` приводит как рабочие примеры (дословно, с пометкой «OK»):

```
let v: Math.Vec2 = Math.Vec2 { x: 1.0, y: 2.0 };  // OK
let n: int32 = Math.Util.neg(5);                   // OK
```

Фактически:
- `Math.Vec2` как **тип** вообще не парсится: `error: expected '=' in variable declaration, got Dot` —
  `parse_type_expr` не умеет квалифицированные имена. Экспорт `pub struct` и `pub type` из модуля
  **недостижим**: тип нельзя даже назвать.
- `Math.Util.neg(5)` — `error: cannot use 'Math.Util' as a value here`: `check_call` разбирает только
  `Ident.field(...)`, вложенный `Module.Namespace.fn` не поддержан ([semantic.cppm:1316-1357](src/semantic/semantic.cppm#L1316-L1357)).
  То же обещание в `semantics.md §14` («Доступ извне: M.Namespace.identifier»).
- Методы импортированных структур недоступны в принципе: таблица `methods_` живёт в анализаторе
  каждого модуля отдельно и между модулями не передаётся.

Примеры в `examples/dops/a2_20_modules` и `a3_14_visibility` аккуратно обходят всё это, ограничиваясь
`Module.fn()` (в `Lib.herta` даже комментарий «без cross-module»). Спецификацию нужно привести к
фактическим возможностям — или доделать код.

### Н-2. Видимость методов (`pub`) не проверяется нигде; у полей уровней доступа нет вовсе

ТЗ A.2.12 требует: «Уровни доступа (`public`/`private`) для полей и методов с проверкой в семантике:
private-члены доступны только из методов своего типа». Проверка:

```
impl C {
    pub fn get(self: C) int32 { ... }
    fn secret(self: C) int32 { ... }   // приватный
}
fn main() int32 {
    let c: C = C { v: 21 };
    print(c.secret());   // компилируется и работает — проверки нет
}
```

`MethodInfo.is_pub` заполняется, но в `check_call` не читается ни для инстанс-, ни для статических
методов. А поскольку кросс-модульные вызовы методов невозможны (Н-1), флаг `pub` на методах не
срабатывает **вообще никогда**. Поля структур синтаксически не имеют модификаторов (всегда публичны,
что `semantics.md §13.3` фиксирует) — но формулировка ТЗ A.2.12 просит уровни доступа и для полей.

### Н-3. Указатель невозможно проверить на null

```
if p == null { ... }   // error: operator '==' not defined for '*int32' and '*void'
```

`check_binary` не обрабатывает указатели ни для `==`, ни для `!=`. В языке **нет никакого способа**
узнать, нулевой ли указатель, кроме как поймать runtime-ошибку. Для A.2.18 («Определить нулевой
указатель и поведение при его разыменовании») формально достаточно, но `null` без возможности
сравнения — полуфабрикат, и в спеках это ограничение не зафиксировано.

### Н-4. «Зарезервированные» слова из grammar.md не зарезервированы

`grammar.md §2.1` перечисляет `print input exit panic assert len` как ключевые слова, которые
«не могут использоваться как имена». Фактически лексер выдаёт их как идентификаторы, и:

```
var input: int32 = 5;
let s: string = input();   // error: 'input' is not callable — builtin сломан затенением
```

`print`/`assert`/`len` перехватываются в `check_call` по имени **до** просмотра scope, поэтому их
затенение игнорируется (тоже странно, но безвредно), а `input`/`exit`/`panic` — обычные символы
глобального scope и затеняются с поломкой. Вдобавок `null` — ключевое слово в коде
([lexer.cppm:164](src/lexer/lexer.cppm#L164)), но в списке §2.1 его нет.

### Н-5. Отрицательные float-литералы не адаптируются к контексту (асимметрия с int)

```
var a: float32 = 1.5;    // OK
var b: float32 = -1.5;   // error: cannot convert 'float64' to 'float32'
```

`check_expr_ctx` ([semantic.cppm:1050-1064](src/semantic/semantic.cppm#L1050-L1064)) специально
обрабатывает `-<int-литерал>`, но не `-<float-литерал>`. Для int при этом всё работает
(`var i: int8 = -5;` — OK). Это прямой баг против `types.md §5.4/§6` («литералы адаптируются
к контексту»), задевает A.1.8.

### Н-6. `fn main()` принимает любой целочисленный тип возврата

Спека (`grammar.md §3.2`, `semantics.md §12`) требует ровно `fn main() int32`; ТЗ — «функцию `main`
с типом возврата `int`». Код ([semantic.cppm:506](src/semantic/semantic.cppm#L506)) разрешает любой
`intN/uintN`: `fn main() int8 { return 7; }` компилируется и работает. Расхождение мягкое, но спеку
и код надо синхронизировать.

## 4. Расхождения документации с кодом

Сквозная проверка «спека ↔ реализация». Помимо Н-1 (кросс-модульные обещания) и БАГ-2 (таблица §2.1):

1. **`grammar.md §6`, «Полный пример программы» — не работает.** Bubble sort передаёт массив
   по значению в `bubble_sort`/`Utils.swap`; при call-by-value все мутации теряются, программа
   печатает исходный массив `5 3 1 4 2`. Проверено запуском. Пример противоречит семантике
   собственного языка (реальный `examples/bubble_sort.herta` честно возвращает массив — спеку
   нужно поправить так же).
2. **`semantics.md §7.8` противоречит `semantics.md §5`.** §7.8: «Функция должна быть объявлена
   **до** места вызова (forward declarations не поддерживаются)». §5 (таблица): функции —
   «двухпроходный резолв, взаимная рекурсия разрешена». Код соответствует §5: взаимная рекурсия
   работает (проверено). §7.8 — устаревший текст.
3. **`types.md §2.4.5` противоречит коду и report.md.** «Многобайтные символы (Unicode сверх ASCII)
   в литералах в v1 не поддерживаются» — фактически лексер и парсер полностью разбирают 1–4-байтные
   UTF-8 char-литералы (`'й'` → codepoint 1081, пример `a1_2_utf8` этим гордится, report.md заявляет
   это как A.1.2). types.md устарел — а именно на нём держится заявка A.1.2.
4. **`semantics.md §13.1` противоречит §1 и коду.** §13.1: «на данный момент параметры всех функций
   иммутабельны». Код делает параметры мутабельными ([semantic.cppm:628](src/semantic/semantic.cppm#L628)),
   и пример в §1 сам мутирует параметр (`x = x * 2`).
5. **`grammar.md §2.1`** — ключевые слова `print/input/exit/panic/assert/len` не зарезервированы
   (Н-4); `null` есть в коде, отсутствует в списке.
6. **`grammar.md §2.4`** — в таблице операторов нет унарного `&` (взятие адреса) и `*`-как-deref
   (в §3.4 они есть); `->` заявлена, но не реализована (М-3).
7. **`grammar.md §4`** — таблица встроенных функций неполна: нет `assert`, `len`, `sleep_ms`,
   `inf`/`nan`, `int_to_string`/`float_to_string`, `parse_int`/`parse_float` (все есть в
   `semantics.md §10` и в коде).
8. **README.md** ссылается на несуществующие `impl_plan.md` и каталог `inc/herta/` («публичные
   заголовки») — заголовков нет, проект на модулях.
9. **`semantics.md §10` про `parse_int`:** «Лишние пробелы или суффиксы — также ошибка распознавания»
   и «возвращается 0» — код соответствует; но runtime `herta_parse_int` возвращает признак успеха,
   который эмиттер игнорирует — язык не может отличить `"0"` от мусора. Спека это честно фиксирует,
   ок; упоминаю для полноты.
10. **`codegen.md`**: `clang-22 -O1 prog.ll src/codegen/runtime.c` — фактическая команда включает
    `-Wno-override-module`; мелочь.

## 5. Базовые требования ТЗ — статус

| Требование | Статус | Комментарий |
|---|---|---|
| Лексика: ключевые слова, идентификаторы, литералы, escape, комментарии | ⚠️ | Всё есть; но «зарезервированность» builtin-имён не соблюдена (Н-4) |
| Ошибки лексера (незакрытая строка, обрыв) | ✅ | Проверено: диагностика с позицией, exit 1 |
| Синтаксис: полная грамматика, рекурсивный спуск, остановка на 1-й ошибке | ✅ | |
| Семантика: имена, scope, типы, поток управления | ⚠️ | Проверки на месте; но shadowing сломан на этапе кодогена (БАГ-1) |
| `break`/`continue` вне цикла, `return` в void, мутабельность `let` | ✅ | Проверено |
| Неинициализированные переменные | ✅ | Инициализатор обязателен синтаксически |
| Рекурсивные структуры / циклы алиасов — ошибка компиляции | ✅ | Через top-down резолв, `unknown type` (задокументировано в §5) |
| Типы: int/uint/float/bool/char/string/void/array/struct | ✅ | |

## 7. Качество кода

Общее впечатление — код аккуратный и читается хорошо: единый стиль, содержательные комментарии
по-русски у каждого модуля (требование ТЗ выполнено), осмысленные имена, `std::expected` + `DiagnosticSink`
без глобального состояния и исключений — ровно как просит ТЗ.

Замечания:

- **[semantic.cppm:896-899](src/semantic/semantic.cppm#L896)** — `check_assign` вызывает `check_expr`
  для цели уже после ручной проверки корня; для цели `*p = v`, где `p` объявлен как `let`, запись
  разрешена (мутабельность прослеживается только по `root_ident`, который Deref не раскручивает).
  Это осознанная семантика указателей? В спеке не зафиксировано.
- **[llvm_emit.cppm:1289-1293](src/codegen/llvm_emit.cppm#L1289)** — `mod_funcs_[target_mod][...]`
  вернёт nullptr и разыменуется, если callee не найден; при корректной семантике недостижимо, но
  `assert`/понятный abort был бы уместнее сегфолта.
- **[llvm_emit.cppm:357-358](src/codegen/llvm_emit.cppm#L357)** — декларации `i64*`/`double*`
  (typed pointers) в остальном opaque-ptr модуле; современный LLVM это ещё принимает, но стоит
  унифицировать на `ptr`.
- **runtime.c:72-93** — `herta_next_int` не используется ни из IR, ни из деклараций эмиттера — мёртвый код.
- **ir.cppm:746-763** — `lower_field` для Namespace/Module возвращает «псевдо-имя» Var с точкой
  в имени и комментарием «lower_call перехватит до сюда» — хрупкое место, ровно тут живёт Н-1.
- Char-сравнения `<`/`>` реализованы в эмиттере ([llvm_emit.cppm:1024-1039](src/codegen/llvm_emit.cppm#L1024)),
  но семантика их запрещает — мёртвый код (или наоборот, задел: тогда спека types.md §2.4.5 против).
- Тесты: юнит-покрытие фаз хорошее, e2e ловит runtime-ошибки и коды возврата. Но ни один тест
  не покрывает shadowing, вложенные lvalue-присваивания и `&поле` — ровно там, где баги. Добавить
  регрессионные кейсы на БАГ-1..4.

## 8. Приоритетный план действий

1. **БАГ-1 (shadowing)** — уникализация имён при lowering. Нарушение базы, блокер допуска.
2. **БАГ-2/БАГ-3** — либо честный lowering lvalue-цепочек (GEP по цепочке до корневой alloca),
   либо запрет в семантике + правка semantics.md §2.1. Тихая потеря данных недопустима даже в учебном компиляторе.
3. **БАГ-4 + Н-3** — отклонять `print(ptr)` в семантике; добавить `==`/`!=` для указателей (тривиально: `icmp eq ptr`).
4. **A.1.7** — доделать вывод типа возврата функций (report уже заявляет его).
5. **Н-1/A.3.14** — квалифицированные типы `M.Type` и `M.NS.fn()`, проверка `is_pub` методов.

   §13.1 (мутабельность параметров), §13.3 (кросс-модульные примеры), §2.1 (`a.b.c`), grammar.md §2.1

   README (битые ссылки), report.md (16→15 кейсов, убрать заявку вывода типа возврата — или реализовать).
