# Отчёт по проекту «Компилятор языка Herta»

## 1. Описание задачи

Спроектировать собственный язык программирования и реализовать для него
полнофункциональный компилятор на C++23: лексический и синтаксический анализ,
семантическая проверка, генерация исполняемого кода либо интерпретация.

Язык Herta — статически типизированный, с явным указанием мутабельности
(`let`/`var`), номинальной системой типов, лексической областью видимости,
модульной системой и арена-моделью управления памятью для строк. Полная
спецификация — в каталоге [`specs/`](specs/).

## 2. Архитектура компилятора

Компилятор реализован как последовательный pipeline из независимых фаз;
каждая фаза — отдельный C++20 модуль, каждая принимает на вход результат
предыдущей и не зависит от деталей её реализации.

```
Исходник (.herta)
   ↓
 [Лексер]            herta.lexer       — поток токенов
   ↓
 [Парсер]            herta.parser      — AST (Recursive Descent)
   ↓
 [Семантика]         herta.semantic    — аннотированный AST, таблицы типов/методов
   ↓
 [Lowering → IR]     herta.ir          — трёхадресный код
   ↓
 [LLVM emitter]      herta.llvm    → .ll → clang → нативный x86-64 ELF
```

Каждая фаза изолирована в своём пространстве имён (`herta::lexer`,
`herta::parser`, …) и не имеет доступа к глобальному состоянию. Драйвер
([`herta.driver`](src/driver/driver.cppm)) оркестрирует все фазы и
дополнительно решает задачу multi-module компиляции:

- рекурсивно загружает `.herta`-файлы по `import`-зависимостям;
- детектирует циклы импортов через раскраску DFS (white/gray/black);
- запускает фазы в топологическом порядке зависимостей;
- передаёт scope экспортов между анализаторами для cross-module name resolution.

### Файловая структура

```
src/
├── common/      common.cppm       — SourceLocation, SourceFile, DiagnosticSink
├── lexer/       lexer.cppm        — лексический анализатор
├── parser/      ast.cppm          — иерархия AST
│                parser.cppm       — синтаксический анализатор (Recursive Descent)
├── semantic/    semantic.cppm     — символьные таблицы, проверка типов
├── ir/          ir.cppm           — IR + lowering
├── codegen/     llvm_emit.cppm    — текстовый эмиттер LLVM IR
│                runtime.c         — C-runtime, линкуется в итоговый бинарь
├── driver/      driver.cppm       — оркестратор, multi-module loader
└── main.cpp                       — CLI
specs/           grammar.md, semantics.md, types.md, codegen.md
tests/           lexer/, parser/, semantic/, driver/, ir/, e2e/
examples/        hello.herta, calc.herta, bubble_sort.herta,
                 v1_features.herta, MathLib.herta, lib_demo.herta
```

## 3. Обоснование проектных решений

### 3.1 C++23 и `import std;`

Проект использует **именованные модули C++20** для всех фаз компилятора и
**стандартный модуль `import std;`**. Это даёт чистую модель компоновки без
заголовочных файлов, ускоряет инкрементальную сборку и заодно соответствует
требованию C++23 в ТЗ.

Цена решения: `import std;` сейчас работает только в связке **Clang ≥ 22 +
libc++ + Ninja + CMake ≥ 4.0**. Это сужает поддержку компиляторов (g++ и
MSVC из ТЗ — задокументированное ограничение), но даёт самый современный
C++-toolchain. Альтернатива (вернуться к заголовкам) была отвергнута: модули
учебно полезнее.

### 3.2 Метод синтаксического разбора

Парсер реализован методом **рекурсивного спуска** ([parser.cppm](src/parser/parser.cppm)),
как требует ТЗ. Выражения разбираются классическим способом «по таблице
приоритетов» в виде нескольких взаимно-рекурсивных функций (`parse_or`,
`parse_and`, `parse_eq`, …), без отдельного Pratt-парсера. Подход
максимально прозрачен для учебного контекста.

AST — иерархия классов с виртуальным `dump()`, единое владение через
`std::unique_ptr<T>`. Это менее «модно», чем `variant`, но даёт явные имена
узлов и удобные `dynamic_cast` для walk-ов.

### 3.3 Диагностика

ТЗ запрещает глобальные состояния ошибок и использование исключений для
потока диагностики. Реализовано через:

- `std::expected<T, std::string>` — для фаз, возвращающих результат;
- `DiagnosticSink` — общий «сток» диагностик, передаётся ссылкой
  в конструкторы фаз и заполняется по мере обнаружения проблем;
- единый формат `<file>:<line>:<column>: error: <message>` ([common.cppm](src/common/common.cppm));
- `throw` не используется нигде, кроме внутренних non-recoverable
  ситуаций в стандартной библиотеке.

Все фазы останавливаются на первой ошибке (требование базы); собранные
диагностики печатаются единым блоком через `DiagnosticSink`.

### 3.4 Выбор бэкенда — почему два пути

ТЗ предлагает три варианта финальной фазы (нативный x86-64 NASM, LLVM IR,
интерпретация). Выбран путь **LLVM IR + clang**: дёшево даёт нативный
бинарь и не требует ручного управления регистрами/ABI/строками в asm.
Текстовая эмиссия (а не использование C++ API libLLVM) выбрана как более
учебно прозрачная и без огромных compile-time затрат.

## 4. Реализованные дополнительные задания

| Код  | Описание | Краткое решение |
|------|----------|-----------------|
| **A.1.1** | Числовые типы 8–64 бит со знаком и без | int8/16/32/64, uint8/16/32/64, float32/64; литералы покрывают весь диапазон uint64; суффиксы размера `42i8`/`255u8`/`2.5f32`; корректные знаковые/беззнаковые операции в LLVM |
| **A.1.2** | UTF-8 в строках и символах | Лексер разбирает char-литералы из 1–4 байт UTF-8 → codepoint (uint32); строки — UTF-8 байты; `len(s)` — байты по semantics |
| **A.1.7** | Автоматический вывод типов | `:=` для переменных; тип возврата функций и методов можно опустить — выводится по `return`-инструкциям тела (semantics.md §7.8.2) |
| **A.1.8** | Неявное widening числовых типов | По таблице `types.md §5.4`; адаптация литералов к контексту (включая отрицательные и float32 с проверкой диапазона); в LLVM вставляется `sext`/`zext`/`sitofp` в точке использования |
| **A.2.12** | Методы структур и видимость членов | instance-методы (`obj.m()`) и static (`T.m()`); валидация `self`; методы без `pub` приватны — вызываются только из методов своего типа; `priv`-поля недоступны вне методов типа (semantics.md §13.6) |
| **A.2.18** | Указатели | `*T`, `&x`, `*p` (rvalue и lvalue), `null` + runtime null-check, сравнения `p == q` / `p != null` |
| **A.2.20** | Модули | `module Name;`, `import Name;`, рекурсивная загрузка `.herta`, проверка имя ↔ файл, обнаружение циклов через DFS |
| **B.2.1** | Промежуточное представление (IR) | Линейный трёхадресный код, `--dump-ir` |
| **A.3.9** | Обобщённые и сырые указатели | `*void` / `*byte` raw pointers, тип `byte` (non-arithmetic, cast'ы в целые и ==/!=), приведения указателей; **function pointers не реализованы** |
| **A.3.14** | Модульная система с контролем видимости | `pub` обязателен для экспорта; кросс-модульно доступны pub-функции (`M.f`, `M.NS.f`), pub-типы (`M.T` как тип, литерал, cast), статические и инстанс-методы pub-типов; не-`pub`-имена отвергает семантика |

## 5. Известные ограничения

1. **Toolchain.** Из-за `import std;` компилятор собирается только Clang 22
   с libc++ + Ninja + CMake ≥ 4.0. g++/MSVC из ТЗ не поддерживаются.
2. **`&` только на переменных.** Адрес поля/элемента (`&s.f`, `&a[i]`)
   запрещён семантикой: при value semantics это был бы адрес временной
   копии. Вложенные lvalue-присваивания (`m.points[i].x = …`) при этом
   полностью работают через write-back-лоуэринг (semantics.md §2.1).
3. **Function pointers (A.3.9).** Не реализованы — `&fn` на функции даёт
   ошибку компиляции с подсказкой. Reasonably-доделаемо, но скоп не требовал.
4. **Адресная арифметика, malloc/free.** Не реализованы.
5. **Стандартная библиотека на языке (A.3.15).** Не реализована: требует
   указателей, динамической памяти и обобщённых типов, что выходит за рамки
   v1. Есть пример `MathLib.herta`, показывающий, что библиотечный модуль
   на самом Herta работает.
6. **Exhaustive return-path analysis.** Семантика не требует, чтобы
   каждый путь не-void функции заканчивался `return`; при «падении с конца»
   LLVM-бэкенд эмитит `unreachable`, что приводит к UB в случае ошибки
   программиста. Для учебного компилятора приемлемо.
7. **Память для строк** — арена (malloc без free). Достаточно для учебных
   программ.
8. **Имена структур глобально уникальны.** Бэкенд держит плоскую таблицу
   структур: одноимённые структуры в разных модулях не поддерживаются.
9. **Вывод типа возврата** видит только объявления выше по файлу; взаимная
   рекурсия функций с выводимыми типами невозможна (semantics.md §7.8.2).

## 6. Сборка и запуск

### 6.1 Зависимости

- CMake ≥ 4.0
- Ninja
- Clang ≥ 22 с libc++ (для `import std;`)
- POSIX-совместимая ОС (Linux, WSL)

### 6.2 Сборка

```bash
cmake -G Ninja -S . -B build -DCMAKE_CXX_COMPILER=clang++-22
cmake --build build
```

Доступны target'ы `build` (по умолчанию), `run`, `debug`, `clean`.

Исполняемый файл компилятора — `build/myc`.

### 6.3 CLI

```bash
./build/myc <source.herta>                # → нативный бинарь
./build/myc <source.herta> -o prog        # → бинарь с указанным именем
./build/myc <source.herta> --run          # → собрать и запустить
./build/myc <source.herta> --emit-llvm    # → вывести .ll
./build/myc <source.herta> --dump-tokens  # → токены
./build/myc <source.herta> --dump-ast     # → AST
./build/myc <source.herta> --dump-ir      # → трёхадресный IR
```

Код завершения программы — значение, возвращённое из её `main`.

### 6.4 Тестирование

```bash
ctest --test-dir build --output-on-failure
```

Шесть тест-сьютов покрывают все фазы:

| Сьют | Что проверяет |
|------|---------------|
| `lexer.tokens`    | разбор всех видов токенов |
| `parser.parse`    | парсинг всех конструкций грамматики |
| `semantic.check`  | проверка типов, scope, мутабельности, методов |
| `driver.modules`  | multi-module компиляция, циклы, pub visibility |
| `ir.lowering`     | корректность lowering |
| `e2e.run`         | end-to-end: компилирует кейс через `myc --run` и проверяет stdout + exit code (25 кейсов, включая регрессии на shadowing, вложенные lvalue, указатели и литералы) |

## 7. Демонстрационные программы

В каталоге [`examples/`](examples/):

- `hello.herta` — простейший вывод строки;
- `calc.herta` — арифметика, ветвление, циклы;
- `bubble_sort.herta` — сортировка с возвратом массива (демонстрация
  value-семантики и проблемно-ориентированной структуры программы);
- `v1_features.herta` — char-литералы, UTF-8 (`'й'` → codepoint 1081),
  binary/hex/decimal-литералы, массивы, len, equality, assert;
- `MathLib.herta` + `lib_demo.herta` — multi-module: библиотечный модуль с
  `pub`/private функциями, импорт и квалифицированный вызов.

Запуск:

```bash
./build/myc examples/lib_demo.herta --run
```
